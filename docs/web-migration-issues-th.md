## 2. ปัญหาที่ 1 (สำคัญที่สุด) — เว็บอ่านเวลาหน้าจอของมือถือไม่ได้

นี่คือปัญหาหลักที่ต้องตัดสินใจก่อนอย่างอื่น

หัวใจของโครงงานเราคือ "เอาเวลาที่ไม่ใช้หน้าจอ มาแลกเป็นความก้าวหน้าของสัตว์เลี้ยง"
ซึ่งต้องอาศัยการอ่านข้อมูลเวลาใช้งานหน้าจอจากระบบปฏิบัติการ

**ข้อเท็จจริงทางเทคนิค:**

- Android ใช้ `UsageStatsManager` — เป็น API ระดับระบบปฏิบัติการ
  **เรียกใช้ได้เฉพาะแอปที่ติดตั้งลงเครื่องจริงเท่านั้น**
- iOS ใช้ Screen Time API (Family Controls) — เงื่อนไขเดียวกัน และต้องขออนุมัติจาก Apple ด้วย
- **เว็บเบราว์เซอร์ไม่มี API ใด ๆ ที่เข้าถึงข้อมูลนี้ได้เลย**
  และไม่มีสิทธิ์ (permission) ใดที่ผู้ใช้จะกดอนุญาตให้เว็บไซต์อ่านข้อมูลนี้ได้
  เพราะเป็นข้อจำกัดด้านความปลอดภัยของทั้ง Android และ iOS
  ไม่ใช่ข้อจำกัดของเครื่องมือที่เราเลือกใช้

**แปลว่า:** ถ้าเปลี่ยนเป็นเว็บล้วน ๆ 100% ระบบจะ **ไม่สามารถ** ติดตามเวลาปลอดหน้าจอได้โดยอัตโนมัติ
ซึ่งกระทบโดยตรงกับวัตถุประสงค์ข้อ 3.1 และ 3.2 ในข้อเสนอโครงงาน
และกระทบความน่าเชื่อถือของผลการวิจัย เพราะข้อมูลจะกลายเป็นข้อมูลที่ผู้ใช้กรอกเอง (self-report)

## 3. ปัญหาที่ 2 — โค้ดที่เขียนไปแล้ว ไม่ตรงกับข้อเสนอโครงงาน

ข้อเสนอโครงงานที่ส่งไปแล้ว ระบุเทคโนโลยีไว้อีกแบบหนึ่ง ซึ่งต่างจากของจริงเกือบทั้งหมด

| หัวข้อ | ข้อเสนอโครงงานเขียนไว้ | โค้ดจริงในรีโป |
|---|---|---|
| Framework | React Native + Expo (TypeScript) | Kotlin + Jetpack Compose |
| แพลตฟอร์ม | Android **และ iOS** | Android อย่างเดียว |
| State | Zustand | Compose State + ViewModel |
| Backend | Supabase (PostgreSQL) | Firebase Firestore |
| Animation | Lottie + Reanimated | Compose Canvas |
| Local Storage | AsyncStorage | Room |

**ต้องตัดสินใจว่า:** จะแก้ข้อเสนอโครงงานให้ตรงกับของจริง หรือจะแก้โค้ดให้ตรงกับข้อเสนอ

โดยทั่วไปการขอแก้เอกสารให้ตรงกับสิ่งที่ทำจริงจะง่ายกว่ามาก แต่ต้องคุยกับอาจารย์ที่ปรึกษาก่อน
และถ้าตัดสินใจไม่ทำ iOS จริง ๆ ต้องแก้ทั้งขอบเขตและกลุ่มตัวอย่างในเอกสารด้วย

## 4. ปัญหาที่ 3 — ระบบยังเก็บข้อมูลวิจัยไม่ได้

โครงงานนี้ไม่ใช่แค่ทำแอป แต่ต้องเก็บข้อมูลไปวิเคราะห์ผล (paired t-test, Pearson correlation)
ตอนนี้ยังไม่มีส่วนนี้เลย

1. **ข้อมูลปลอมปนเข้ามาได้** — ใน `ScreenTimeTracker.kt` ถ้าผู้ใช้ยังไม่ให้สิทธิ์
   ระบบจะ **คืนค่าปลอม 145 นาที** และรายชื่อแอปสมมติ แทนที่จะแจ้งว่า "ยังไม่ได้รับสิทธิ์"
   ถ้าปล่อยไว้ ข้อมูลปลอมนี้จะปนเข้าไปในผลวิจัยโดยที่เราไม่รู้ตัว
   **ต้องแก้ก่อนเริ่มเก็บข้อมูลจริง**
2. **ไม่มีการบันทึก log เซสชันขึ้นฐานข้อมูล** — ตอนนี้ sync แค่สถานะสัตว์เลี้ยงขึ้น Firestore
   แต่ไม่ได้เก็บประวัติรายวัน / รายเซสชัน ที่จำเป็นต่อการวิเคราะห์
3. **ไม่มีรหัสผู้เข้าร่วม (Participant ID) และไม่มีหน้ายินยอมเข้าร่วมวิจัย (Consent)**
4. **ยังไม่มีแบบวัด SAS-SV และ PSQI ในระบบ** — ตอนนี้ต้องเก็บนอกระบบ เช่น Google Form
5. **ยังไม่มีฟังก์ชัน export ข้อมูลเป็น CSV** สำหรับเอาไปวิเคราะห์สถิติ

## 6. ทางเลือกในการทำเป็นเว็บ (3 แนวทาง)

### แนวทาง A — แอป Android เก็บข้อมูล + เว็บเป็นหน้าแสดงผล (แนะนำ)

แอป Android ที่มีอยู่ ทำหน้าที่เป็น "ตัวเก็บข้อมูล" อ่านเวลาหน้าจอแล้วส่งขึ้น Firestore
จากนั้นทำ **เว็บไซต์แยกต่างหาก** ที่ดึงข้อมูลจาก Firestore เดียวกัน มาแสดงเป็นหน้า
สัตว์เลี้ยง สถิติ อันดับ และหน้า export ข้อมูลสำหรับทีมวิจัย

- ข้อดี: ยังติดตามเวลาหน้าจอได้อัตโนมัติ → **ผลวิจัยยังน่าเชื่อถือ**
- ข้อดี: โค้ดที่ทำไปแล้วเกือบทั้งหมดยังใช้ต่อได้ ไม่ต้องเขียนใหม่
- ข้อดี: ทีมได้ "เว็บไซต์ที่โฮสต์จริง + เชื่อมฐานข้อมูล" ตามที่หัวหน้าทีมต้องการ
- ข้อดี: อาจารย์เปิดเว็บดูข้อมูลผู้เข้าร่วมทั้งหมดได้เลย
- ข้อเสีย: ผู้เข้าร่วมวิจัยยังต้องติดตั้งแอปลงมือถืออยู่ดี
- ข้อเสีย: ต้องดูแล 2 ส่วน (แอป + เว็บ)

### แนวทาง B — ทำเป็นเว็บล้วน (PWA) ทิ้งแอปเดิม

เขียนใหม่ทั้งหมดเป็นเว็บ เช่น React / Next.js ผู้ใช้กด "เริ่มเซสชันปลอดหน้าจอ" ในเบราว์เซอร์
แล้วใช้ Page Visibility API + Wake Lock API ตรวจว่าออกจากหน้าเว็บไปหรือยัง

- ข้อดี: เป็นเว็บ 100% ตามที่หัวหน้าทีมต้องการ ไม่ต้องติดตั้งอะไร เข้าผ่านลิงก์ได้เลย
- ข้อดี: ใช้ได้ทั้ง Android และ iOS ทันที (ตรงกับขอบเขตในข้อเสนอโครงงาน)
- **ข้อเสีย (ร้ายแรง): วัดเวลาหน้าจอจริงไม่ได้** ต้องให้ผู้ใช้กรอกเองจาก Digital Wellbeing
- ข้อเสีย: ผู้ใช้โกงง่ายมาก แค่เปิดหน้าเว็บค้างไว้แล้วไปเล่นแอปอื่น เบราว์เซอร์ไม่รู้
- ข้อเสีย: ต้องเขียนใหม่ทั้งหมด โค้ด Kotlin ที่ทำมาถูกทิ้ง
- ข้อเสีย: ต้องแก้ระเบียบวิธีวิจัยในข้อเสนอโครงงาน เพราะข้อมูลเปลี่ยนเป็น self-report

### แนวทาง C — เว็บเป็นตัวหลัก + แอป Android ตัวเล็กไว้ส่งข้อมูล

เว็บไซต์เป็นตัวเกมหลัก (สัตว์เลี้ยง ไอเทม สถิติ) ส่วนแอป Android เหลือแค่ตัวเล็ก ๆ
ที่ทำหน้าที่อ่าน UsageStats แล้วอัปโหลดขึ้น Firestore อย่างเดียว ไม่มี UI

- ข้อดี: ได้ข้อมูลเวลาหน้าจอจริง และเว็บเป็นตัวหลักตามที่หัวหน้าทีมต้องการ
- ข้อเสีย: ต้องรื้อ UI ของแอปเดิมทิ้งแล้วไปเขียนใหม่บนเว็บ — งานเยอะกว่าแนวทาง A
- ข้อเสีย: ผู้ใช้ต้องติดตั้งแอปอยู่ดี (เหมือนแนวทาง A) แต่ประสบการณ์ใช้งานแย่กว่า
  เพราะต้องสลับไปมาระหว่างแอปกับเว็บ

| หัวข้อ | A: แอป + เว็บแสดงผล | B: เว็บล้วน | C: เว็บหลัก + ตัวเก็บข้อมูล |

| ได้เว็บที่โฮสต์จริง | ได้ | ได้ | ได้ |
| ต้องติดตั้งแอป | ต้อง | ไม่ต้อง | ต้อง |
| รองรับ iOS | ไม่ | ได้ | ไม่ |
| โค้ดเดิมที่ใช้ต่อได้ | เกือบทั้งหมด | เกือบไม่ได้เลย | บางส่วน |
| ปริมาณงานที่เหลือ | น้อย | มากที่สุด | ปานกลาง–มาก |

## 7. ข้อเสนอแนะ

**แนะนำแนวทาง A** เพราะตอบโจทย์ทั้งสองฝั่งได้พร้อมกัน
หัวหน้าทีมได้เว็บไซต์ที่โฮสต์จริงและเชื่อมฐานข้อมูล ส่วนงานวิจัยยังได้ข้อมูลเวลาหน้าจอที่วัดจริง
ไม่ใช่ข้อมูลที่ผู้ใช้กรอกเอง และโค้ดที่ทีมทำมาแล้วไม่ถูกทิ้ง

ถ้าทีมยืนยันเลือกแนวทาง B จริง ๆ ก็ทำได้ แต่ **ต้องยอมรับล่วงหน้า** ว่า
ตัวเลขเวลาหน้าจอจะเป็นข้อมูล self-report และต้องเขียนข้อจำกัดนี้ไว้ในรายงานอย่างชัดเจน

**เรื่องฐานข้อมูล: ตกลงใช้ Firebase / Firestore** (ไม่ใช่ Supabase ตามที่เขียนในข้อเสนอ)
เพราะในโค้ดเชื่อมต่อไว้แล้ว มี Google Sign-In พร้อม และมี Firebase Hosting ใช้โฮสต์เว็บได้ในตัว

(เดิมใช้โปรเจกต์ `gen-lang-client-0770902376` ที่ Google AI Studio สร้างให้อัตโนมัติ
ซึ่งผูกกับบัญชีของเพื่อนในทีม ทำให้คนอื่นเข้าไม่ได้ จึงย้ายมาสร้างใหม่ให้เป็นของกลาง)

ข้อควรระวัง: Firestore เป็น NoSQL ทำสถิติยากกว่า SQL ดังนั้นต้องเพิ่มฟังก์ชัน

## 8. สิ่งที่ต้องตัดสินใจในที่ประชุม

1. เลือกแนวทางไหน — **A, B หรือ C**
2. จะแก้ข้อเสนอโครงงานให้ตรงกับของจริงไหม (Kotlin แทน React Native, Firebase แทน Supabase)
3. **ยังทำ iOS อยู่ไหม** — ถ้าไม่ทำ ต้องแก้ขอบเขตในเอกสาร
4. กลุ่มตัวอย่างสรุปกี่คน — เอกสารเขียนขัดกันเอง
